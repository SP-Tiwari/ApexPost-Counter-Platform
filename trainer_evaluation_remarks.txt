Satya: ApexPost Counter Platform Review

Score: 78 / 100

This ZIP is byte-for-byte identical to the "ApexPost-Counter-Platform-master.zip" I reviewed earlier today, so the result is the same; I've only reformatted the remarks to match the other reviews.

What You Did Well
Clean architecture. Domain, Application, Infrastructure and Web are separate projects with dependencies pointing inward. All saving and loading goes through IApexPostRepository, and there are four test projects.
A careful domain model that protects itself.
Money, Sku, BranchCode, Weight and Dimensions are real value objects.
The basket follows a clear Open → Paid → Voided or Refunded lifecycle.
Each business rule is its own class: TransactionProcessingRule, ShippingWeightLimitRule, MoneyOrderIdentityVerificationRule and TransactionVoidRefundRule.
Business rules enforced in the domain:
stock can never go negative
inactive staff, or staff from another branch, are rejected
a money order above the threshold needs a successful identity check
the parcel weight limit depends on the service level
refunds need a Branch Manager from the same branch and a reason
an inactive branch can't make sales
Identity documents are masked inside the domain object. The full number can't be stored; when I ran the app, only ****4567 was saved.
Strong authentication.
Passwords are hashed with PBKDF2 (600,000 iterations) and compared in constant time.
A dummy password check runs for unknown emails, so response time doesn't reveal which accounts exist.
Credentials are stored separately from the main data.
Every cookie is checked against the current staff record, so a deactivated or reassigned user is signed out immediately.
Most of the middleware works when run:
The correlation ID is checked before it is reused.
Errors are returned as Problem Details.
Request timing is logged in a finally block, so failures are timed too.
Maintenance mode returns Retry-After, while /health stays available.
Security headers and HSTS are set.
The API key is compared in constant time: 401 for a missing or wrong key, 500 if none is configured.
The IP allowlist works.
Both rate limits work: login, and partner (429 after 5 requests).
CORS allows only the exact configured origin.
389 tests across the domain, application, infrastructure and web layers.
What Was Great
Safe under concurrent sales. I sent 20 one-unit sales at the same time against 10 units in stock. Exactly 10 succeeded, 10 were rejected with 409, and stock ended at 0. Two things make this work: the data is read, changed and written back under one lock, and every save goes through a temporary file. Submitting the same form twice is also rejected.
Bad configuration stops the app instead of guessing. Startup refuses invalid settings, and if prices, tax rates or thresholds are missing, the affected workflow stops rather than using a made-up value.
Honest self-assessment. docs/week-2-gap-analysis.md openly lists what is incomplete.
What Needs Improvement
Voids and refunds don't work end to end. I confirmed both by running the app.

Sales are saved as Paid immediately, but Void only accepts an Open basket, so voiding a completed sale always returns 409.
A refund changes the status but doesn't return the stock.
Allow voiding a Paid sale, and return stock on both void and refund.

Money orders aren't part of the counter basket.

They sit on a separate Branch-Manager-only form, so counter clerks can't issue them.
Because of that, the "verified in the same transaction" rule isn't met.
The "check passed" box is ticked by the user, and the fee is typed in by hand.
Make money orders a basket line, take the fee from configuration, and have the system decide the verification result.

The basket is limited. It allows only one product line plus optional shipping. Let staff add several products.

The daily sales report has no real dates. Transactions don't store a date, so every day shows all-time totals. Add an OccurredAtUtc field to each transaction.

Notifications aren't raised. LowStockNotificationRule and HighValueMoneyOrderNotificationRule exist but are never called. Add an event or observer that raises all four required notifications.

The partner endpoint and some protections are missing.

There is no /integration/parcel-status endpoint, so the API key, IP, CORS and partner-limit protections guard nothing by default.
Protection is set by URL path rather than by an attribute on the endpoint.
Admin pages have no IP restriction.
There are no named policies such as BranchManagerOnly or SameBranchOnly.
Several Part B C# features are missing:

Task.WhenAll (for example, on the dashboard)
ValueTask with a cache
timeouts on a simulated courier lookup
the field keyword
custom attributes with a cached reflection validator
events
What you did use is used well: the extension member, records, pattern matching, generics, Func and SemaphoreSlim.

Filters and audit.

The audit records redirects as status 200; a successful sign-in was logged as 200 instead of 302.
It audits every action, including page views (GETs). Limit it to business actions.
ValidationActionFilter only acts on [ApiController] controllers, and there are none, so it never runs.
AUDIT-SAMPLE.json is a single hand-written entry. Export real lines from audit-events.jsonl instead.
The demo is hard to start.

The demo staff have no credentials and no password is documented, so there's no way to sign in out of the box.
The App_Data/SeedData files aren't used and don't match the C# seed (25 inventory rows versus 150).
Provide a one-command demo setup with documented logins.

Smaller items:

The dashboard is static.
There is no shipping label preview or catalogue page.
The ADRs have no "Alternatives considered" sections.
TreatWarningsAsErrors is not enabled.

Final Assessment
Satya, the engineering quality is high. The domain modelling, authentication and concurrency-safe storage are excellent. The score is held back because several core counter workflows are incomplete: voids can't be used, money orders sit outside the basket, the daily report has no real dates, and the partner endpoint and notifications are missing.

Priorities, in order:

Fix void and refund, including returning stock.
Put money orders into the basket.
Add transaction dates.
Wire up the notifications.
Add the parcel-status endpoint and the missing C# features.
The foundation is solid, so these are additions rather than rewrites.
