ApexPost Logistics – Week 3: SQL Server Persistence, Data Access Patterns and Offline-First Counter Terminals (EF Core 10, Repository/Unit of Work)

Lab Problem Statement:

Project background

ApexPost Logistics now runs the Counter Platform you built in Week 2: an ASP.NET Core MVC application with a secure middleware pipeline, action-filter auditing and JSON-file persistence behind repository interfaces.

The pilot branches have shown that JSON files cannot support thousands of branches. They cannot handle concurrent clerks selling the same stock, reliable multi-step transactions, or fast reports for head office and auditors. ApexPost needs a proper system of record.

This week you will move the platform to Microsoft SQL Server, accessed through EF Core 10. You will design the schema properly, tune it with evidence, and apply clean data-access patterns: Repository, Unit of Work, DTOs and the separation of domain and persistence models. All of it continues in the same ApexPost solution.

Week 3 goal

Replace the JSON repositories with SQL Server and EF Core 10 behind the same application interfaces. Prove the business logic did not change.
Design the relational schema properly, index it based on evidence, and use stored procedures where they add value.
Apply the Repository, Unit of Work, DTO and domain/persistence separation patterns from Labs 13–16 deliberately, not mechanically.
Keep everything from Week 2 working: middleware, filters, authentication, auditing and tests.
Part A: Relational schema design (SQL Server)

Create your own database, ApexPostDb. Never use a shared training database.
Design normalized tables (3NF) for at least:
Branches, Counters, Staff, Roles
Products, ProductCategories, BranchStock, StockAdjustments
ShippingZones, ShippingRates, Shipments
MoneyOrders, IdentityVerifications
CounterTransactions, TransactionLines, Payments
AuditEntries
For every table, define:
primary keys and foreign keys, with the delete behaviour you chose and why;
UNIQUE constraints (BranchCode, Sku, staff email);
CHECK constraints (quantities ≥ 0, Amount > 0, allowed Status values, weight limits);
DEFAULT constraints, and audit columns (CreatedAtUtc, CreatedBy, ModifiedAtUtc).
Add a rowversion concurrency column on BranchStock and CounterTransactions.
Use correct data types:
decimal(18,2) for money;
date or datetime2 in UTC;
varchar for codes, nvarchar for names.
Store identity documents masked only (for example, the last 4 characters). Never store the full document number. Enforce this in the domain and reflect it in the schema (column length).
Deliver:
an ER diagram in DESIGN.md;
a normalization note listing three anomalies your design prevents;
the generated schema script (dotnet ef migrations script --idempotent).
Part B: SQL queries, transactions and integrity

Write and save reporting queries (in a /sql folder) using INNER and LEFT JOINs, GROUP BY and HAVING:
daily branch sales split by retail and services;
branches with no sales today (a LEFT JOIN case);
top 10 products by revenue per region;
shipping volume by zone and service level;
money orders and identity verifications per branch.
Show a multi-table transaction in T-SQL that records a sale, its lines and the stock decrement atomically. Use BEGIN TRAN, TRY…CATCH, SET XACT_ABORT ON, XACT_STATE() and THROW.
Demonstrate blocking with two SSMS sessions (one updating stock, one reading it). Explain what you observed and the isolation level involved.
Document how your design avoids deadlocks: a consistent table access order and short transactions.
Part C: Index optimization and execution plans

Choose at least four real workloads, for example:
the low-stock report by branch;
daily sales by branch and date;
shipment search by zone and service level;
money-order search for auditors.
For each workload:
capture a baseline: the actual execution plan, plus logical reads and CPU time from SET STATISTICS IO/TIME;
design a candidate index (composite, covering or filtered), and justify the order of its key columns and any INCLUDE columns;
measure again on realistic data volumes;
record the write overhead and storage cost.
Fix at least one non-SARGable predicate, for example rewriting YEAR(TransactionDate) = 2026 as a date range. Show the plans before and after.
Investigate one estimated-vs-actual row mismatch (stale statistics or parameter sensitivity) and explain it.
Deliver PERFORMANCE.md with:
saved .sqlplan files or screenshots;
before/after tables (reads, CPU, plan shape);
your conclusions.
Never invent numbers. If a small dataset still produces scans, explain why rather than hiding it.
Part D: Stored procedures

Write at least three stored procedures. Each must use CREATE OR ALTER and SET NOCOUNT ON, validate its parameters, and raise meaningful errors with THROW:
usp_DailyBranchSales (@BranchCode, @Date): retail vs services totals.
usp_LowStockReport (@BranchCode = NULL, @Threshold): optional parameters. Explain your choice between OPTION (RECOMPILE) and the alternatives.
usp_AdjustStock (@BranchCode, @Sku, @Delta, @Reason, @ChangedBy): transactional, using TRY…CATCH and XACT_ABORT. It also writes a StockAdjustments history row.
Call the procedures from EF Core with parameterized APIs only (ExecuteSqlAsync, FromSql or SqlQuery). No string concatenation.
Add a least-privilege note: which database role and permissions the application login needs.
Write an ADR explaining why each procedure is a procedure and not a LINQ query. “Stored procedures are faster” on its own is not an accepted reason.
Part E: EF Core 10 mapping, migrations and querying

In the Infrastructure project, create:
ApexPostDbContext;
IEntityTypeConfiguration classes (Fluent API) for every entity;
value converters for value objects (Money, Sku, BranchCode, Weight);
owned types where they fit (for example, Address and Dimensions).
Use code-first migrations:
InitialCreate, plus at least one follow-up migration (for example, adding an index or a column);
review every migration before applying it;
generate an idempotent SQL script;
never call EnsureCreated() in application code.
Seed data through migrations or a seeding service:
at least 5 branches, 20 staff, 30 products and 10 zones/rates;
at least 200 historical transactions, so that the indexes and reports are meaningful.
Querying rules:
AsNoTracking projections into DTOs for every read screen and report;
Include only where tracked aggregates are needed;
AsSplitQuery where a single query would multiply rows (cartesian explosion);
no N+1 queries, proven with EF Core command logging in Development.
Writes:
a counter sale decrements BranchStock and saves the transaction, its lines and the payment in one SaveChangesAsync;
use ExecuteUpdateAsync for a set-based price revision.
Concurrency: two clerks selling the last unit at the same time must not drive stock negative. Handle DbUpdateConcurrencyException with a clear message (HTTP 409 or a view error).
Explicit transactions: wherever you mix SaveChangesAsync with a stored procedure or ExecuteUpdate, use an explicit transaction together with an execution strategy.
Use ToQueryString() to capture the generated SQL for at least three important queries, and include it in PERFORMANCE.md.
Part F: Data access patterns (Repository, Unit of Work, domain vs persistence)

Dependency direction:
Domain references nothing.
Application defines the interfaces.
Infrastructure implements them with EF Core.
Web is the composition root.
Create specific repositories for aggregates, for example IBranchRepository, IProductRepository, IStockRepository, ICounterTransactionRepository, IStaffRepository and IAuditStore.
Repositories stage changes only. They never call SaveChanges.
No repository returns IQueryable.
Add IUnitOfWork with SaveChangesAsync and an optional ExecuteInTransactionAsync.
One commit per use case.
Repositories, the unit of work and the DbContext are all scoped, so they share one DbContext per request.
Domain vs persistence:
Keep rich domain entities with private setters and methods (for example Sale.AddLine, BranchStock.Remove(quantity), MoneyOrder.RequireVerification).
Map them with the Fluent API, and use shadow properties for rowversion and audit columns.
Create a separate persistence entity plus a mapper for at least one aggregate (for example, IdentityVerification with masked storage) and justify it in an ADR.
DTOs and mapping:
request DTOs for every POST/PUT, with validation;
response/view-model DTOs for every screen;
explicit mapping: input model → application command → entity (as in the Input Model to Data Model Mapper lab);
prove that over-posting Status, Id or audit fields has no effect.
Query/command separation:
reports and dashboard reads go through query services (AsNoTracking projections or stored procedures);
writes go through command services or handlers (repositories + unit of work);
no separate databases are required. State this explicitly.
Prove the refactor: the Week 2 business-rule unit tests must pass unchanged against the new persistence layer.
Part G: Integration with the existing platform

MVC screens now read and write SQL Server through services:
dashboard;
catalogue and stock;
counter transactions, voids and refunds;
money orders and identity verification;
reports.
Reports use query services or stored procedures:
daily branch sales;
low stock;
shipping volume by zone and service level;
money orders and identity verifications per branch.
AuditActionFilter now writes to the AuditEntries table through IAuditStore. Audit writes must not break the business transaction. Decide whether they share the unit of work or are stored separately, and justify the choice.
Exceptions map to Problem Details:
DbUpdateConcurrencyException → 409;
unique violations → 409;
not found → 404;
domain errors → 400.
The connection string comes from user-secrets in Development. Never commit credentials.
Part H: Testing and evidence

Unit tests (no database):
domain rules: stock, identity verification, weight limits, voids and refunds;
application services with fake repositories and a spy unit of work (commit once, or never on failure).
SQL Server integration tests, using a disposable test database or container (never the development database):
repository mapping and translation;
a failed sale rolls back the stock and transaction rows together;
a concurrency conflict on stock returns 409;
the stored procedures return the expected results.
API/MVC tests with WebApplicationFactory, using a test database:
a sale persists correctly;
a void requires the Branch Manager role;
the reports return the expected totals;
errors return Problem Details.

Constraints

.NET 10 and C# 14, with nullable reference types enabled and zero build warnings.
SQL Server is the only database for this week.
Allowed packages:
Microsoft.AspNetCore.* and Microsoft.Extensions.*;
Microsoft.EntityFrameworkCore.* (SqlServer, Design, Tools);
xUnit and Microsoft.AspNetCore.Mvc.Testing.
Anything else needs trainer approval and an ADR.
All database access is asynchronous where the API supports it, with a CancellationToken passed through. No .Result, .Wait() or Thread.Sleep.
No string-concatenated SQL anywhere: EF Core LINQ, parameterized raw SQL and parameterized stored procedures only.
The DbContext, repositories and unit of work are scoped. No static or singleton DbContext.
No secrets in source control. Use fictional data only. Identity documents stay masked everywhere: database, logs and audit entries.
Program.cs remains a composition root. No business logic in endpoints, middleware, filters or repositories.
